# 《小满村》研发技术选型建议

## 文档定位

本文件是给研发团队的**技术选型建议稿**，承接 `tech-data-qa.md` 的客户端/服务端边界、存档结构和反作弊要求，给出从引擎、配表工具链、服务端、数据库到部署运维的具体技术栈推荐与取舍理由。

约束前提（来自现有设计）：

- 平台：微信小游戏首发，横屏 16:9。
- 视角：2.5D 俯视 / 轻 isometric 像素风。
- 玩法：农场经营 + 县城集市交易 + NPC 剧情 + 节日活动。
- 社交：前期异步多人（好友摊位快照、好友订单、互买、吆喝、群分享）。
- 经济：核心收益、库存、交易、排行榜、离线收益必须服务端权威校验。
- 数据驱动：所有数值和内容走配置表，避免硬编码。
- 商业化：广告、内购、月卡、排行榜、限时活动。

## 选型总览

| 层 | 推荐方案 | 备选 | 关键理由 |
| --- | --- | --- | --- |
| 客户端引擎 | **Cocos Creator 3.8 LTS** | LayaAir、自研 | 国内微信小游戏生态最成熟，2D/像素管线好，TS 原生，分包/资源管理完善 |
| 开发语言（客户端） | **TypeScript** | — | 与引擎一致，类型安全，便于配表代码生成 |
| 客户端架构 | **数据驱动 + 模块化 MVC**，局部 ECS（农场地块/集市顾客） | 全量 ECS | 经营类系统多为状态机和配表驱动，无需全量 ECS |
| 配表工具链 | **Luban**（Excel → 多语言代码 + 二进制/JSON） | 自研 Excel 导出脚本 | 策划用 Excel，导出强类型 TS，支持校验和增量 |
| 服务端语言 | **Go**（核心服）或 **Node.js + TS**（快速期） | Java | Go 性能/并发好、部署轻；Node 与客户端同语言、迭代快 |
| 服务端框架 | Go: 自研轻量 HTTP + gRPC / Node: **NestJS** | Egg.js、Gin | 经济为短连接请求为主，无需重型框架 |
| 主存档库 | **MySQL/PostgreSQL**（玩家强一致数据） | TiDB（后期扩容） | 关系型清晰、事务保证交易/库存一致 |
| 缓存/会话/排行榜 | **Redis** | — | 排行榜 ZSet、限流、离线时长、热数据缓存 |
| 异步社交存储 | Redis（摊位快照缓存）+ MySQL（订单/收益落库） | — | 快照读多写少，订单需持久 |
| 接入层 | 微信登录 + 自建网关 | 微信云开发（仅原型期） | 长期需要自建以满足反作弊和成本控制 |
| 部署 | 容器化（Docker）+ 云厂商 K8s / 轻量服务器 | — | 弹性扩容，灰度发布 |
| 数据分析 | 自建埋点上报 + 数仓（ClickHouse） | 第三方（如有合规需求） | 埋点字段已在 `tech-data-qa.md` 定义 |

## 1. 客户端引擎

### 推荐：Cocos Creator 3.8 LTS

理由：

- **微信小游戏适配最成熟**：官方一键发布、分包、引擎裁剪、内存与首包体积优化经验丰富，社区案例多。
- **2D / 像素风管线好**：支持 Sprite Atlas 图集、TiledMap、骨骼动画（Spine/DragonBones），像素风可关闭抗锯齿、设置 Point 过滤。
- **TypeScript 原生**：与配表代码生成、服务端（若用 Node）语言统一，降低心智成本。
- **资源系统**：AssetBundle + 远程加载，便于热更新美术资源和活动内容（小游戏允许远程资源下载）。

### 为什么不选其他

- **LayaAir**：性能不错、体积小，但生态和文档活跃度弱于 Cocos，2D 工具链不如 Cocos 顺手，可作备选。
- **Egret**：已基本停止主线维护，不推荐新项目。
- **Unity（WebGL/微信转换）**：包体大、首屏慢、与微信小游戏内存限制冲突明显，不适合该品类的轻量定位。
- **纯自研 Canvas/WebGL**：开发成本过高，不值得。

### 像素风与横屏要点

- 设计分辨率建议 **1280×720**（16:9），`Canvas` 用 `fitHeight` 适配，左右两端按更宽的全面屏（19.5:9）留安全区，避开横屏时位于左右一侧的刘海/灵动岛。
- 微信小游戏在 `game.json` 设 `"deviceOrientation": "landscape"`。
- 像素资源统一倍率（如 32px tile），关闭纹理过滤抗锯齿，避免边缘糊。
- 地图用 2.5D 俯视：可用 Tilemap + 手摆装饰对象 + 深度排序（按 y 轴排序遮挡）。
- 镜头横向卷动 + 缩放 + 自动寻路，充分利用横屏宽画幅（见 `ui-flow.md`）。

## 2. 客户端架构

### 分层

```
表现层（UI / 场景 / 动画）
  ↕
逻辑层（系统：农场 / 钓鱼 / 挖矿 / 集市 / 任务 / 社交）
  ↕
数据层（运行时存档 State + 配置表 Config）
  ↕
网络层（请求封装 / 协议 / 重连 / 离线队列）
```

建议：

- **数据驱动**：作物、鱼、矿、配方、NPC、任务、活动全部读配表（见 `tech-data-qa.md` 配置表清单），逻辑只处理规则。
- **状态集中管理**：用单一运行时 State 树映射 `tech-data-qa.md` 的存档结构（player_profile / time_state / inventory / farm_state ...），便于序列化、断点续玩和服务端校验对齐。
- **局部 ECS 可选**：农场大量地块、集市大量顾客实体可用轻量 ECS/对象池优化性能，其余系统用普通模块即可，不强求全量 ECS。
- **时间系统以服务端为准**：本地只做插值表现，跨天结算和离线收益由服务端下发（反作弊重点）。

## 3. 配表工具链

### 推荐：Luban

- 策划用 **Excel** 维护数值（最低门槛），Luban 导出：
  - **强类型 TS 代码**（客户端直接 `import` 带类型的配置）。
  - **二进制或 JSON 数据**（运行时加载，二进制更省体积/更快）。
- 支持**字段校验、引用检查、枚举、本地化**，对应发布前检查里的「配置表缺失、ID 重复、非法引用」。
- 同一份配表可同时供客户端和服务端使用，保证数值一致。

### 命名规范

- ID 命名必须与 `design.md` 内容生产规范一致（如 `crop_xxx`、`fish_xxx`、`npc_xxx`）。
- 建立配表 Git 仓库或子目录，配表变更走 Code Review，导出产物纳入 CI 校验。

## 4. 服务端

### 语言与框架

两条路线，按团队情况选：

| 路线 | 适用 | 说明 |
| --- | --- | --- |
| **Go + 轻量 HTTP/gRPC** | 追求性能、长期 | 并发好、部署为单二进制、内存占用低，适合经济/交易高频校验 |
| **Node.js + NestJS + TS** | 快速验证、小团队 | 与客户端同语言，配表类型可复用，迭代快；后期热点可用 Go 重写 |

经济系统以**短连接 HTTP/RPC 请求**为主（操作-校验-落库），**前期不需要长连接实时同步**，符合异步多人定位。

### 核心服务模块

- 账号/登录：微信 code2session 换 openid，签发自有 token。
- 存档服务：读写玩家 State，关键写操作做幂等和版本号（防并发覆盖）。
- 经济服务：收益结算、库存扣减、交易成交、订单生成与校验（服务端权威）。
- 社交服务：好友摊位快照、好友订单、互动次数限制、防互刷检测。
- 时间/离线服务：以服务端时间为准，离线时长与收益封顶。
- 活动/运营服务：liveops 配置下发、限时活动、排行榜。
- 商业化服务：广告发奖幂等、内购平台订单校验、月卡跨天发放。

## 5. 数据存储

| 用途 | 选型 | 说明 |
| --- | --- | --- |
| 玩家强一致存档 | **MySQL / PostgreSQL** | 交易、库存、货币需事务；按 `tech-data-qa.md` 存档模块分表/分 JSON 列 |
| 缓存 / 排行榜 / 限流 | **Redis** | 排行榜用 ZSet；摊位快照、热点配置、互动次数计数 |
| 大体量埋点 / 分析 | **ClickHouse**（或云数仓） | 新手漏斗、经济、留存埋点的离线分析 |
| 后期水平扩容 | TiDB（备选） | 玩家量级上来后替换 MySQL |

存档建议：用「关系表 + JSON 字段」混合——强一致字段（货币、库存关键项）用列；松散结构（farm_state、装饰摆放）用 JSON，兼顾一致性与灵活性。

## 6. 异步社交实现思路

- **摊位快照**：玩家开摊时把摊位配置 + 在售商品快照写入 Redis（带 TTL）+ 落 MySQL。好友访问时读快照，不依赖对方在线。
- **好友购买**：买方下单 → 服务端校验快照库存与价格 → 扣库存、记收益挂账 → 卖方下次上线领取并收到反馈。
- **互动次数/防刷**：吆喝、点赞、互买都有每日次数上限，配合 IP/设备/关系链异常检测（对应反作弊表）。
- **群分享**：用微信分享卡片带 query 参数，回流时归因 `share_type` 埋点。

> 前期不做实时联机。若后续做集市同场实时互动，再引入 WebSocket 长连接网关（如 Go 自建或基于云厂商网关），避免一开始过度设计。

## 7. 工程化与协作

- **语言/规范**：TypeScript 全栈（若服务端用 Node），统一 ESLint + Prettier；Go 端用 gofmt + golangci-lint。
- **版本管理**：Git，分支策略 trunk-based 或 git-flow；配表、客户端、服务端可单仓多目录（monorepo）或分仓。
- **CI/CD**：提交触发——配表导出校验、客户端构建、服务端单测与镜像构建；支持灰度发布（对应「灰度发布建议」）。
- **资源管线**：美术按玩法模块出图集，纳入 AssetBundle，活动资源走远程加载热更。
- **环境**：dev / staging / prod 三套，prod 配置与密钥走密管，不入库。

## 8. 第三方与平台能力

| 能力 | 方案 |
| --- | --- |
| 登录 | 微信 `wx.login` + 服务端 code2session |
| 支付 | 微信小游戏虚拟支付（注意平台政策与分成）/ 安卓苹果合规处理 |
| 广告 | 微信激励视频广告，服务端幂等发奖（防重复领奖） |
| 分享/转发 | 微信分享 API + 带参回流归因 |
| 排行榜 | 微信开放数据域 + 自建 Redis 榜（自建更可控、可反作弊） |
| 推送/回流 | 微信订阅消息（赶集开摊、作物成熟、好友订单提醒） |
| CDN | 远程资源、AssetBundle 走 CDN 加速首屏与热更 |
| 防沉迷/合规 | 实名、未成年时段与消费限制，按平台要求实现 |

## 9. 微信小游戏专项注意

- **首包体积**：微信主包有体积上限，必须分包；首屏只加载新手村+开场动画所需资源，其余按需远程加载。
- **内存**：低端机内存紧张，控制图集数量、及时释放离场资源、用对象池。
- **开放数据域**：好友排行榜数据在隔离的开放数据域渲染，注意通信限制。
- **审核与合规**：内容（敏感词、台词、伪文字）、广告与内购合规、隐私协议，对应发布前检查表。
- **断网兜底**：弱网/断网/重连/重复点击/异常退出都要有兜底，关键操作做幂等。

## 10. 分阶段技术路线

| 阶段 | 技术目标 | 服务端 | 重点 |
| --- | --- | --- | --- |
| **原型 / MVP** | 验证「种田→加工→赶集→好友购买」闭环 | 可先用**微信云开发**快速起步，或最小 Node 服务 | 配表工具链先搭好，避免后期返工；服务端权威校验从第一天就做经济相关 |
| **垂直切片** | 一个完整季节内容 + 真存档 + 真异步社交 | 迁移到自建服务（Go/Node）+ MySQL + Redis | 存档结构定型、埋点接入、反作弊基础 |
| **首发** | 四季内容、节日活动、排行榜、商业化 | 容器化 + 灰度 + 数仓 | 性能/兼容/合规/经济闭环全面验证 |

> 建议：即使原型期用云开发，**经济权威校验、配表工具链、存档结构**这三件事要从一开始按目标架构设计，因为它们最难返工。

## 11. 主要技术风险

| 风险 | 应对 |
| --- | --- |
| 首屏加载慢 / 包体超限 | 分包 + 远程资源 + 首屏资源最小化 |
| 低端机性能/内存 | 对象池、图集控制、离场释放、降帧策略 |
| 经济被刷 | 服务端时间权威、库存校验、幂等发奖、异常检测（见反作弊表） |
| 配表膨胀难维护 | Luban 强类型 + 校验 + CI，ID 规范统一 |
| 存档结构后期难改 | 存档加版本号，预留 JSON 扩展字段，做迁移脚本 |
| 异步社交数据一致 | 快照 + 服务端成交校验 + 挂账领取，避免双花 |

## 一句话结论

**客户端 Cocos Creator 3.8 LTS + TypeScript，配表用 Luban，服务端 Go（或快速期 Node/NestJS）+ MySQL + Redis，全程数据驱动、经济服务端权威、异步社交用快照 + 挂账。** 原型期可借微信云开发提速，但配表工具链、存档结构和经济校验要从第一天就按目标架构设计。
